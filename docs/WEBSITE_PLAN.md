# Slipstream Oracle Website Design Plan

> **Project:** Slipstream Oracle  
> **Purpose:** A premium, Formula 1-inspired static website for presenting the predictions, models, drivers, and generated data of the Slipstream Oracle ML project.

This document defines the visual direction, website structure, assets, data sources, metadata, behaviour, and implementation constraints for the website.

---

# 1. About the Website

Slipstream Oracle is a Formula 1-styled website used to present the predicted race results generated by the Slipstream Oracle ML pipeline.

The website should feel like a combination of:

- A modern F1 broadcast interface
- A professional race-engineering data system
- A premium motorsport website
- A futuristic analytics dashboard
- A cinematic Formula 1 experience

The design should use modern UI techniques while remaining lightweight and fast.

## Technology

Use only:

- HTML
- CSS
- Vanilla JavaScript
- JSON
- CSV

Do **not** introduce:

- React
- Next.js
- TypeScript
- A backend server
- A database
- An API server
- Server-side rendering

The website is intended to be deployed using **GitHub Pages**.

## Core Principle

> **Slipstream Oracle performs the computation. The website presents the computation.**

The website must not execute the ML model. It must consume the files generated by Slipstream Oracle and turn them into an elegant visual experience.

---

# 2. Visual & Design Direction

The website should be **astonishing, cinematic and unmistakably Formula 1**, while avoiding the appearance of a generic admin dashboard.

## Design Language

Use a combination of:

- F1-inspired motorsport aesthetics
- Premium dark UI
- Glassmorphism
- Frosted translucent panels
- Subtle borders
- Soft backdrop blur
- Strong typography
- High-contrast data presentation
- Cinematic imagery
- Subtle motion
- Engineering/dashboard visual language

Glassmorphism should be used intelligently. Panels should feel like premium glass surfaces layered over the background rather than excessive transparent boxes everywhere.

## Suggested Visual Characteristics

- Dark cinematic base
- Deep blacks / charcoal surfaces
- White and near-white typography
- Red motorsport accents inspired by Formula 1
- Controlled secondary accent colours
- Subtle gradients
- Thin luminous borders
- Background image/video depth
- Large editorial typography
- Compact technical labels
- Sharp numerical presentation

Do not make the site visually noisy.

The overall feeling should be:

> **“A Formula 1 prediction laboratory operating from the pit wall.”**

## F1 Styling

The website may take visual inspiration from modern Formula 1 broadcast graphics, timing screens and race engineering interfaces, but should remain an original Slipstream Oracle identity rather than attempting to reproduce an official F1 website.

Use motorsport-inspired elements such as:

- Position indicators
- Timing-style numbers
- Race-status labels
- Driver/team identifiers
- Technical metadata
- Grid-inspired layouts
- Subtle diagonal/track-inspired shapes
- Motion cues inspired by racing telemetry

- Home

# 5. Home

The Home page is the cinematic entry point to Slipstream Oracle.

## F1 Logo

At the top-left area below/around the main navigation, display:

```text
assets/f1_logo.png
```

The F1 logo should be sized carefully so it is:

- Clearly visible
- Weighted
- Not oversized
- Visually balanced with the hero content

## Background Video

Use:

```text
assets/bg_f1.mp4
```

Requirements:

- Autoplay
- Muted
- Loop
- Plays inline
- Covers the hero area
- Does not interfere with text readability
- Use an appropriate dark/blurred overlay
- Apply sufficient visual blur/depth so foreground content remains highly readable

The video should feel like a cinematic race environment rather than a normal HTML video element.

The implementation should gracefully fall back to a static background if video playback is unavailable.

## Hero Title

Below the F1 logo, display a strong hero title:

```text
Slipstream Oracle
```

The title should have a distinctive signature/driver-autograph feeling for **“Slipstream”**, while **“Oracle”** should have a clean technical/premium treatment.

The result should feel like a custom motorsport identity rather than a normal website heading.

## Hero Description

Use a concise description communicating that Slipstream Oracle is a machine-learning-driven Formula 1 prediction and analytics system.

Suggested direction:

> **Where race data meets machine learning. Slipstream Oracle transforms qualifying performance, historical form and race data into data-driven Formula 1 predictions.**

The description should remain short enough to preserve the cinematic impact of the hero section.

## Home Supporting Elements

The Home page may include tasteful supporting elements such as:

- Current season indicator
- “Powered by Slipstream Oracle” label
- Current/featured Grand Prix
- Model status
- Small technical metrics
- Scroll indicator

These should remain secondary to the hero identity.

# 6. Drivers

The Drivers tab contains the driver details for the current season.

## Driver Cards

Create a visually rich card for every driver defined in `drivers.json`.

Each card must display the metadata defined by the driver metadata file:

- Driver name
- Driver number
- Team
- Driver description
- Headshot

## Headshot Presentation

Driver images should **not** simply appear as small rectangular thumbnails.

Render the headshots as premium full-body/portrait compositions where the driver remains partially cropped by the card design, with visibility extending approximately to the driver's hip where the source image allows it.

The image should blend naturally into the card using:

- Gradient masking
- Soft shadows
- Controlled transparency
- Glass layers
- Team-inspired accent details

The driver should remain the visual focus of the card.

## Driver Card Interaction

Cards may include tasteful hover effects such as:

- Slight elevation
- Image movement/parallax
- Border illumination
- Metadata reveal
- Subtle scale transition

Avoid excessive animation.

## Driver Metadata

Use:

```text
drivers.json
```

as the canonical driver metadata source.

# 7. Models

The Models tab presents the machine-learning models used by Slipstream Oracle.

For the current version, display a model card for:

### Random Forest

The card should communicate that Random Forest is the current regression model used by Slipstream Oracle.

The card can include:

- Model name
- Model category
- Short explanation
- Current usage status
- Relevant model information if available

Keep this section expandable for future models.

Possible future models may include other regression/ensemble approaches, but they should not be implemented unless their data and implementation are actually available.

# 8. DataHub

DataHub is the core data presentation section of the website.

It presents Grand Prix prediction datasets generated by Slipstream Oracle.

## GP Cards

Each available Grand Prix should be represented by a visually rich card displaying its race name.

Example directory:

```text
predictions/2026/Monaco_Grand_Prix/
```

The display name should convert:

```text
Monaco_Grand_Prix
```

to:

```text
Monaco Grand Prix
```

The user should never see the raw underscore-based directory name in the UI.

## Dataset Requirement

A Grand Prix should only be treated as available when the expected prediction file exists:

```text
Final_Data.csv
```

A GP directory existing by itself is not sufficient.

## Current Data Location

The website is located inside the `website/` directory.

Prediction data is located relative to it at:

```text
../predictions/2026/GP_NAME/Final_Data.csv
```

Example:

```text
../predictions/2026/Azerbaijan_Grand_Prix/Final_Data.csv
```

## Dynamic GP Discovery — Experimental

The desired long-term behaviour is for DataHub to discover available GP folders and automatically create cards when valid prediction datasets are present.

**Important GitHub Pages constraint:** a browser cannot reliably enumerate arbitrary directories in a static GitHub Pages deployment. Therefore, do not create a backend merely to solve directory discovery.

For the first implementation:

- Keep the dynamic filesystem/folder-discovery logic commented.
- Use a sample GP card to validate the UI.
- Clearly comment the experimental discovery section.
- After testing, the discovery mechanism may be enabled/reworked using a static manifest or generated index file.

A future static manifest could contain entries such as:

```json
[
  {
    "name": "Azerbaijan Grand Prix",
    "slug": "Azerbaijan_Grand_Prix",
    "file": "../predictions/2026/Azerbaijan_Grand_Prix/Final_Data.csv"
  }
]
```

Do not introduce a backend for this feature.

## DataHub Card Behaviour

A GP card may display:

- Grand Prix name
- Season
- Dataset availability
- Prediction status
- Number of drivers if available
- “View Prediction” action

The card should lead to a detailed prediction/data view when implemented.

---

# 9. CSV Data Contract

The website consumes pre-generated Slipstream Oracle CSV files.

The frontend must not modify the underlying dataset.

The exact CSV schema supplied by the Oracle pipeline should be treated as the source of truth.

At minimum, prediction-related UI should be prepared to work with fields such as:

- Driver
- Team
- QualiPosition
- GridPosition
- PredictedFinish
- PredictedPosition

If additional columns are present, they should only be displayed when explicitly mapped to a UI element.

Do not invent data when a CSV field is missing.

---

# 10. Data → UI Mapping

The website should separate raw data from presentation.

Example driver mapping:

```text
Final_Data.csv
      ↓
Driver code (e.g. VER)
      ↓
drivers.json["VER"]
      ↓
Driver metadata
      ↓
Driver name + team + number + description + headshot
```

Example prediction mapping:

```text
PredictedPosition
      ↓
Displayed prediction rank

PredictedFinish
      ↓
Model's predicted finishing value

QualiPosition
      ↓
Qualifying position indicator

GridPosition
      ↓
Starting grid indicator
```

The frontend must not confuse `PredictedPosition` with `PredictedFinish`.

---

# 11. Glassmorphism System

Glassmorphism is a core part of the visual language, but it must remain controlled.

Use:

- `backdrop-filter: blur(...)`
- Semi-transparent surfaces
- Thin translucent borders
- Soft shadows
- Subtle inner highlights
- Layered depth

Glass panels should sit naturally over the cinematic background.

Avoid making every element glass. Important content should still have strong visual hierarchy and readable surfaces.

Cards should feel like pieces of a premium race-control interface floating above the background.

---

# 12. Animations & Motion

Animations should reinforce the racing theme without becoming distracting.

Suggested interactions:

- Hero content fade/slide-in
- Smooth tab transitions
- Driver-card entrance animation
- Hover elevation
- Subtle image movement
- Data counter animations where appropriate
- Prediction row transitions
- Glass highlight movement

Respect:

```css
prefers-reduced-motion
```

Do not use animation merely because it is technically possible.

---

# 13. Responsive Design

The website must work properly on:

- Desktop
- Laptop
- Tablet
- Mobile

Mobile should not simply be a compressed desktop layout.

Where appropriate:

- Multi-column driver grids should become single-column/compact grids.
- Large prediction tables may become stacked cards.
- Hero typography should scale responsively.
- Navigation should adapt to small screens.
- Background video must remain performant.

---

# 14. Performance

Despite the cinematic design, the website must remain lightweight.

Requirements:

- Lazy-load non-critical images where appropriate.
- Avoid unnecessary JavaScript libraries.
- Avoid unnecessary dependencies.
- Optimize image rendering.
- Do not preload large assets without reason.
- Background video must not block the page from becoming usable.
- Keep animations GPU-friendly where possible.

The visual richness must not turn the website into a slow application.

---

# 15. Accessibility

The design should remain accessible despite its visual ambition.

Include:

- Meaningful `alt` text for driver images.
- Sufficient text contrast.
- Keyboard-accessible navigation.
- Visible focus states.
- Reduced-motion support.
- Semantic HTML where appropriate.

---

- Databases

---

# 18. Implementation Philosophy

Antigravity is given creative freedom over the visual implementation.

The implementation should prioritize:

1. Astonishing visual quality
2. Formula 1 atmosphere
3. Premium glassmorphism
4. Clear information hierarchy
5. Smooth interaction
6. Performance
7. Maintainable vanilla JavaScript
8. Correct data consumption

Do not hardcode prediction results into HTML.

Do not duplicate driver metadata unnecessarily.

Do not hardcode individual driver image mappings when they already exist in `drivers.json`.

Do not modify the Slipstream Oracle ML pipeline as part of website development.

> **The website is the presentation layer of Slipstream Oracle, not a replacement for the Oracle engine.**

---

# 19. About

The About tab should explain the identity and purpose of Slipstream Oracle.

Suggested content direction:

> **Slipstream Oracle is a personal Formula 1 machine-learning project built around data, experimentation and the pursuit of better race predictions.**
>
> **The system collects Formula 1 data, engineers historical performance features and applies machine-learning models to produce race predictions. The website transforms those outputs into a visual race-control experience.**
>
> **It is not presented as a replacement for Formula 1 expertise or race engineering. It is an experimental data-science project designed to explore what historical racing data can reveal.**

The About section should also contain:

- Project identity
- Technology used
- ML model information
- Data-source acknowledgement where applicable
- Copyright information
- Project/repository link if supplied

Keep the presentation premium and concise rather than turning the page into a long technical document.
